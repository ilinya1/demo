# 学生宿舍管理系统 — 数据库设计说明

> 依据：《HTML原型修改记录.md》"结果 4 — 供建库的字段映射建议" + 原型 `prototype/` 逐字段核对 + 讨论定稿。
> 规范：**逻辑外键**（不加物理 FOREIGN KEY），完整性由后端 Service 保证。
> 同步维护：本文件与 `docs/sql/init.sql` 字段必须保持一致，任何一处改动需同步改另一处。

***

## 一、设计原则与关键约定

1. **逻辑外键**：关联字段以 `_id`（或 `student_id`/`order_no` 等业务键）表示关系，**不建物理外键**。数据一致性由后端 Service 在事务内校验兜底。这是为换取开发灵活、避免删除/迁移阻塞所作的取舍，代价是"数据库不兜底"，故所有写接口必须走统一 Service 校验。
2. **快照冗余（仅 check\_in）**：住宿历史是核心审计读路径，会因调宿产生"同名房间不同时段"多次记录；故 `check_in` 在入住时写入 `student_name/class_name/building_name/room_no/bed_no` 文本快照，**退宿不覆盖**，保证历史可还原、不随主数据漂移。其余记录表（卫生/报修）房间号常年稳定，用 id 关联、join 主数据即可，不加快照。
3. **冗余联动（student.housing\_status）**：学生在住/退宿状态冗余在 `student` 表，由入住/退宿 Service 同步维护，避免每页 join。
4. **枚举统一**：全项目状态枚举见文末《枚举字典》，前端原型与后端取值强一致。
5. **账号体系**：`sys_user` 统一承载管理员与学生登录；学生 `username` 与学号同值并关联 `student_id`。密码字段生产存 **BCrypt 密文**；`init.sql` 演示样本用 `{noop}` 明文占位便于演示，部署时须替换为 BCrypt。

***

## 二、ER 关系总览

```
class ──1:N──> student ──1:1──> sys_user(student_id)
dorm_building ──1:N──> dorm_room ──1:N──> dorm_bed
student ──1:N──> check_in (逻辑外键 student/building/room/bed)
student ──1:N──> checkout_apply
dorm_room ──1:N──> hygiene_record
student ──1:N──> repair_order (含 building/room)
repair_type ──1:N──> repair_order (type_id)
```

一对一：`sys_user.student_id ↔ student.student_id`（学生账号）
其余均为一对多，靠逻辑外键列关联，多侧在"子表"。

## 六、核心业务流转（数据库视角）

1. **入住（管理员 checkin.html）**：选择学生→楼栋→楼层→房间→床位。Service 事务内：校验学生未在住、床位空闲 → 写 `check_in`(在住, 记录快照) + 清空该生历史在住（若有）+ 置 `dorm_bed.status=占用` + 置 `student.housing_status=在住` + 刷新 `dorm_room.status`。
2. **退宿-学生申请（checkout-apply→checkout-audit）**：学生写 `checkout_apply`(待审核)；管理员审核通过→执行退宿（同下），来源 `source=apply`；驳回→写 `reject_reason`。
3. **退宿-直接办理（checkout-audit 直接退宿）**：跳过申请，直接执行退宿，来源 `source=direct`。
4. **退宿执行**：事务内置 `check_in.check_out_time/status=已退宿` + 置 `dorm_bed.status=空闲` + 置 `student.housing_status=已退宿` + 刷新房间状态。
5. **床位查询（room-detail 床位分布）**：查 `dorm_bed` join 在住 `check_in`（或按 bed 空/占）展示每床状态及占用学生。
6. **卫生检查**：写 `hygiene_record`，学生在"我的卫生"按 room\_id 回显。
7. **报修**：学生写 `repair_order`(待处理)；管理员派单写 handler 信息、处理流程改状态；学生按 student\_id 查进度。

## 七、二期扩展预留说明

- **调宿/换床位**：`check_in` 天然支持（原记录退宿 + 新记录入住），无需改表，纯业务逻辑。

- **毕业批量退宿**：`check_in` + `source=direct`，批量接口处理。

- **班级班主任账号**：`sys_user.role` 可扩 `TEACHER`，`class.head_teacher` 已存在。

- **报修催单/评价**：二期 `repair_order` 加字段或建 `repair_feedback` 小表。

- **通知公告 / 水电费 / 违纪**：需要新表，二期再建，本文件届时同步补充。

## 八、QA 常见问题

- **为什么 check\_in 有 5 个快照字段却不算冗余失控？** 因它是不可变历史流水，写入即定格、只读不回头改；快照换来"房号重编/换宿后历史仍准确"，且只存在于核心审计表一张，量小、确定会读（我的宿舍/入住记录），是快照的典型适用场景。

- **为什么卫生/报修不加快照？** 房间号常年不变，id 关联 + join 主数据足够；否则每张记录表都冗余，成本大于收益。

- **为什么不用 physical FK？** 换取开发灵活、避免删除/迁移阻塞；代价是不兜底，故约定所有写操作走 Service 事务校验（见第四节）。
